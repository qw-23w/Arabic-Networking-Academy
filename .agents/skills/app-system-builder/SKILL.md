# بناء الأنظمة التطبيقية

ابنِ نظامًا يحقق حاجة المستخدم ويلائم بنية المشروع الحالية، مع قرارات واضحة قابلة للمراجعة.

## سير العمل

1. افهم هدف المنتج والمستخدمين ومساراتهم. افحص المشروع وتعليمات `AGENTS.md` والأنماط القائمة قبل اقتراح بنية جديدة. اسأل فقط عن المعلومة التي تمنع قرارًا جوهريًا؛ سجّل الافتراضات القابلة للعكس بوضوح.
2. حوّل الطلب إلى نطاق محدد: وظائف أساسية، متطلبات غير وظيفية ذات صلة، خارج النطاق، ومعايير قبول يمكن ملاحظتها.
3. صمّم حدود النظام قبل التنفيذ: المكونات وتدفق البيانات، نموذج البيانات والعلاقات والقيود والفهارس، وسياسات المصادقة والتفويض. صِف عقود API بما يشمل المدخلات والتحقق والاستجابات والأخطاء والترقيم والتكرار الآمن حين يلزم.
4. اعرض خطة تنفيذ قصيرة على شكل شرائح رأسية مرتبة. لكل شريحة، حدّد النتيجة التي يراها المستخدم والملفات أو الطبقات المتوقعة. لا تكتب مواصفات تفصيلية لما لا يحتاجه الطلب.
5. نفّذ شريحة واحدة في كل مرة، وحافظ على السلوك الحالي خارج النطاق. استخدم ترحيلات قابلة للمراجعة لأي تغيير بيانات، وإعدادات للبيئة للأسرار، وفحوص صلاحيات على الخادم لا في الواجهة فقط.
6. تحقّق من معايير القبول والفحوص ذات الصلة إذا طلب المستخدم الاختبار أو كان التحقق جزءًا صريحًا من المهمة. اذكر ما شغّلته وما تعذر تشغيله، ولا تدّعِ اختبار خدمة خارجية لم تُفحص.
7. لخّص البنية والقرارات ونقاط التكامل والخطوة التالية، واذكر المخاطر المتبقية بوضوح.

## معايير الاختيار

- فضّل التقنية والنمط المعتمدين في المشروع. أضف اعتمادًا أو خدمة خارجية فقط إذا كان لهما سبب عملي واضح.
- لا توسّع النطاق بإضافة ميزات متوقعة لكنها غير مطلوبة. ميّز بين مطلب المستخدم واقتراحك.
- لا تنفّذ نشرًا أو ترحيلًا على خدمة حية أو إرسال بيانات خارجية دون تفويض صريح.
- اربط كل قرار قاعدة بيانات أو API بحاجة فعلية ومعيار قبول، ولا تخترع بيانات أو نتائج تشغيلية.
